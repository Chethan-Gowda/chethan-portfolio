# ADR-002 — Content Architecture

**Status:** Approved  
**Date:** 2026-11-06  
**Related Requirements:** REQ-004, REQ-005, REQ-006, REQ-010, REQ-011, REQ-012, REQ-013, REQ-025, REQ-027  
**Related Specifications:** SPEC-004, SPEC-005, SPEC-006, SPEC-008, SPEC-010, SPEC-011, SPEC-012, SPEC-013, SPEC-038, SPEC-039

---

## Context

The portfolio contains several types of professional content:

- Professional experience
- Skills
- Projects
- Certifications and learning
- Presentations and talks
- Professional achievements
- Resume
- About/profile content

The architecture must allow the owner to maintain required content without modifying source code.

At the same time, the portfolio is intentionally small and should not be turned into an unnecessarily complex CMS.

---

## Options Considered

### Option A — Custom Post Type for Every Content Type

Create separate Custom Post Types for:

- Projects
- Experience
- Skills
- Certifications
- Talks
- Achievements

**Advantages:**
- Highly structured
- Each item can be independently managed
- Strong separation of content types

**Disadvantages:**
- Adds unnecessary administrative and architectural complexity
- Introduces more registration and management code
- Over-engineers content that does not require independent lifecycle management

---

### Option B — Use WordPress Pages/Gutenberg for Everything

Manage all portfolio content through normal WordPress pages and Gutenberg.

**Advantages:**
- Very simple
- Minimal custom architecture
- Strong native WordPress integration

**Disadvantages:**
- Projects may become difficult to manage as the portfolio grows
- Project content is less independently structured
- Repeated project fields may become inconsistent

---

### Option C — Hybrid Content Architecture

Use a Custom Post Type for Projects while keeping other portfolio content as structured Gutenberg/page content unless a future requirement justifies a dedicated content type.

**Advantages:**
- Provides structured project management
- Keeps the rest of the architecture simple
- Avoids unnecessary Custom Post Types
- Supports future growth without prematurely designing a large CMS
- Aligns with the project's scope

**Disadvantages:**
- Requires different management approaches for different content
- Some structured content may require carefully designed Gutenberg patterns/blocks

---

## Decision

Use **Option C — Hybrid Content Architecture**.

### Projects

Projects will be implemented as a **Custom Post Type** because projects are expected to be added and updated regularly.

### Experience

Experience will remain structured portfolio content rather than a dedicated Custom Post Type.

It must support:

- Organization
- Role/title
- Employment period
- Responsibilities
- Achievements
- Multiple roles within the same organization
- Current-role identification

### Skills

Skills will be managed as structured grouped content.

The architecture will not introduce numerical proficiency ratings.

### Certifications

Certifications and learning items will be repeatable structured content that can be added or removed independently.

### Talks

Presentations and talks will be repeatable structured content that can be added or removed independently.

### Achievements

Professional achievements will be repeatable structured content that can be added or removed independently.

### Resume

The resume will be maintained as a PDF through the WordPress Media Library.

### About/Profile

Professional profile content will use standard WordPress/Gutenberg content capabilities.

---

## Reason

Projects have a stronger need for independent content management because new projects are expected to be added over time.

The remaining content types are relatively small and do not currently justify separate Custom Post Types.

This approach provides the required maintainability while avoiding unnecessary CMS complexity.

---

## Consequences

### Positive

- Projects have a structured and reusable content model
- Other portfolio content remains simple
- Lower architectural complexity
- Fewer Custom Post Types to maintain
- Easier alignment with the project's small scope
- Supports future extension if requirements change

### Negative

- Different content types will use different editing approaches
- Structured Gutenberg content will need deliberate design
- Future requirements may require revisiting whether additional content types need dedicated structures

---

## Constraints

The architecture must not introduce a Custom Post Type merely for consistency.

A new content type should only be introduced when a concrete requirement demonstrates a need for independent lifecycle management, querying, or structured data.
