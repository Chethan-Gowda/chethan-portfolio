# ADR-005 — Content Editing Strategy

**Status:** Approved  
**Date:** 2026-11-06  
**Related Requirements:** REQ-005, REQ-006, REQ-010, REQ-011, REQ-012, REQ-025, REQ-027  
**Related Specifications:** SPEC-005, SPEC-006, SPEC-010, SPEC-011, SPEC-012, SPEC-025, SPEC-038

---

## Context

The portfolio must allow the owner to maintain content without modifying source code where required.

The content includes:

- Skills
- Projects
- Certifications
- Talks
- Achievements
- Experience

The architecture already establishes a preference for native WordPress capabilities and minimal dependencies.

We therefore need to define how structured content should be edited.

---

## Options Considered

### Option A — Native Gutenberg Only

Use WordPress Gutenberg blocks and block patterns for all content.

**Advantages:**
- Native WordPress functionality
- No additional dependency
- Strong integration with the Block Theme

**Disadvantages:**
- Some structured content requirements may be difficult to model consistently
- Repeated structured data may require careful block design

---

### Option B — ACF-Based Content Management

Use Advanced Custom Fields to model structured content.

**Advantages:**
- Straightforward structured fields
- Useful for repeatable content
- Familiar editorial experience
- Strong control over field structure

**Disadvantages:**
- Adds a dependency
- Some content could be unnecessarily modeled as fields
- Introduces additional maintenance and upgrade considerations

---

### Option C — Custom Gutenberg Blocks for Everything

Build custom blocks for all structured content.

**Advantages:**
- Full control over the editing experience
- Native Gutenberg integration
- Strong content structure

**Disadvantages:**
- Significant development effort
- More custom code to maintain
- Potentially excessive for a simple portfolio

---

### Option D — Native Gutenberg First, With Targeted ACF/Custom Blocks

Use native Gutenberg capabilities wherever they are sufficient.

Introduce ACF only when a specific structured-content requirement justifies it.

Introduce custom Gutenberg blocks only when native capabilities and/or ACF are insufficient.

**Advantages:**
- Minimal architecture
- Native WordPress first
- Flexibility where genuinely required
- Avoids unnecessary custom development
- Supports maintainability

**Disadvantages:**
- Requires decisions on a case-by-case basis
- Some content may use different editing mechanisms

---

## Decision

Use **Option D — Native Gutenberg First, With Targeted ACF/Custom Blocks**.

The implementation priority is:

1. Native WordPress/Gutenberg
2. Existing native block patterns/components
3. ACF when a concrete structured-content requirement justifies it
4. Custom Gutenberg blocks when required

No ACF field group or custom block should be introduced without a documented technical reason.

---

## Reason

The portfolio is intentionally simple.

Using ACF or custom blocks for every content type would create unnecessary architecture.

At the same time, forcing all structured content into generic Gutenberg content could reduce consistency and maintainability.

The hybrid approach provides the required flexibility while maintaining the project's minimal-dependency principle.

---

## Consequences

### Positive

- Native WordPress remains the default
- Reduced dependency footprint
- Structured content can still be modeled appropriately
- Avoids unnecessary custom blocks
- Supports future requirements without prematurely designing them

### Negative

- Different content areas may use different editing mechanisms
- Technical design must justify each non-native implementation
- Some structured-content decisions will be deferred until Technical Design

---

## Constraints

The existence of a requirement for editable content does not automatically justify ACF.

The implementation must first determine whether native Gutenberg capabilities adequately satisfy the requirement.

Any introduction of ACF or custom blocks must be traceable to a requirement or specification.
