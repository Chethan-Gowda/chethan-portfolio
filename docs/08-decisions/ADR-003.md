# ADR-003 — Plugin Strategy

**Status:** Approved  
**Date:** 2026-11-06  
**Related Requirements:** NFR-012, NFR-013, REQ-016–020  
**Related Specifications:** SPEC-016, SPEC-017, SPEC-018, SPEC-019, SPEC-020, SPEC-036, SPEC-037

---

## Context

The portfolio requires several capabilities that could potentially be implemented using WordPress plugins, including:

- Contact forms
- SEO
- Structured content
- Spam protection
- Performance
- Security

The project should remain simple, maintainable, performant, and secure.

The architecture must avoid unnecessary plugin dependencies.

---

## Options Considered

### Option A — Minimal/Native First

Use WordPress core capabilities wherever practical and introduce plugins only when a concrete requirement justifies them.

### Option B — Recommended Plugin Stack

Use established plugins for common functionality such as:

- SEO
- Contact forms
- Security
- Performance
- Custom fields

### Option C — Mostly Custom

Build most functionality directly into the theme and use very few or no functional plugins.

---

## Decision

Use **Option A — Minimal/Native First**.

WordPress core capabilities will be preferred wherever they adequately satisfy the requirements.

A plugin may be introduced only when:

1. WordPress core does not adequately satisfy the requirement.
2. The plugin provides meaningful functionality.
3. The plugin is actively maintained.
4. Its security profile is acceptable.
5. Its performance impact is acceptable.
6. It does not conflict with the approved architecture.
7. Its accessibility impact is acceptable.
8. The dependency can be maintained over the life of the project.

---

## Reason

A personal portfolio does not require a large plugin ecosystem.

Reducing dependencies provides better control over:

- Performance
- Security
- Maintainability
- Accessibility
- Upgrade risk
- Architecture complexity

The strategy also supports the project's goal of learning how to make deliberate technical decisions rather than assembling the site from pre-built plugins.

---

## Consequences

### Positive

- Fewer dependencies
- Lower plugin maintenance burden
- Better control over performance
- Smaller attack surface
- Clearer architecture
- Greater understanding of WordPress core capabilities

### Negative

- Some functionality may require custom implementation
- More responsibility for maintaining custom functionality
- Common functionality may take longer to implement than using an established plugin

---

## Constraints

Plugins must not be added simply because they are popular or convenient.

Every functional dependency must have a documented architectural justification.

The contact form is explicitly handled by ADR-004.
