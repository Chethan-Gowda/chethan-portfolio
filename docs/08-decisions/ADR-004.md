# ADR-004 — Contact Form Architecture

**Status:** Approved  
**Date:** 2026-11-06  
**Related Requirements:** REQ-016, REQ-017, REQ-018, REQ-019, REQ-020, REQ-021  
**Related Specifications:** SPEC-016, SPEC-017, SPEC-018, SPEC-019, SPEC-020, SPEC-021

---

## Context

The portfolio requires a contact form that allows visitors to submit enquiries.

The approved requirements specify:

- Name
- Email
- Subject
- Message
- Required fields
- Server-side validation
- Email validation
- Sanitization
- Accessible validation errors
- Spam protection
- Email delivery
- No WordPress database storage
- Configurable recipient
- Success and failure feedback
- Alternative contact method when delivery fails
- Privacy notice

The project also follows a minimal dependency strategy.

---

## Options Considered

### Option A — WordPress Form Plugin

Use an established third-party WordPress form plugin.

**Advantages:**
- Faster implementation
- Existing validation functionality
- Existing spam protection options
- Established form-processing workflows

**Disadvantages:**
- Adds a plugin dependency
- Introduces additional code and configuration
- Less direct control over implementation
- Potential dependency, performance, accessibility, and upgrade concerns

---

### Option B — Custom WordPress Form

Implement the form using WordPress/PHP and appropriate WordPress core APIs.

**Advantages:**
- No form-plugin dependency
- Direct control over validation and processing
- Direct control over accessibility
- Direct control over data handling
- Fits the minimal-dependency architecture
- Provides useful WordPress development and SDD learning value

**Disadvantages:**
- The project is responsible for maintaining validation and processing
- Spam protection must be deliberately designed
- Email delivery behavior must be tested
- More implementation responsibility than using a plugin

---

### Option C — External Form Service

Use a third-party hosted form service.

**Advantages:**
- External handling of form infrastructure
- Potentially established spam and delivery mechanisms

**Disadvantages:**
- Adds an external service dependency
- Introduces third-party privacy considerations
- Less control over the complete form experience
- May introduce additional performance or integration complexity

---

## Decision

Use **Option B — Custom WordPress Form**.

The contact form will be implemented using WordPress/PHP and appropriate WordPress core APIs.

No dedicated form plugin will be required.

---

## Form Processing Responsibilities

The custom implementation must address:

1. Form rendering
2. Accessible labels and instructions
3. Client-side enhancement where useful
4. Server-side validation
5. Input sanitization
6. Output escaping
7. Nonce/security protection
8. Spam mitigation
9. Email delivery
10. Success feedback
11. Failure feedback
12. Alternative contact method
13. Privacy notice

Server-side validation remains authoritative.

---

## Data Handling

Contact submissions must **not be stored in the WordPress database**.

The implementation must only process the information required to deliver the enquiry.

The recipient email address must be configurable without requiring changes to the form's core implementation.

---

## Reason

The contact form is relatively small and its requirements are clearly defined.

A custom implementation avoids introducing another plugin dependency and provides direct control over:

- Security
- Accessibility
- Data handling
- Performance
- User experience

It also aligns with the project's learning objective of applying SDD to a real WordPress implementation.

---

## Consequences

### Positive

- No form-plugin dependency
- Full control over form behavior
- Clear data-handling model
- Direct alignment with the approved specifications
- Reduced plugin footprint

### Negative

- Validation and processing become project responsibilities
- Spam protection requires deliberate design
- Email delivery requires testing
- Future changes must be maintained within the project

---

## Constraints

The implementation must not introduce unnecessary custom infrastructure.

The project will use appropriate WordPress/core capabilities for:

- Security
- Validation
- Sanitization
- Request processing
- Email delivery

The project will not build a custom mail server or unnecessarily complex spam system.
