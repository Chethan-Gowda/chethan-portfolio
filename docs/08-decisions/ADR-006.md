# ADR-006 — Deployment Architecture

**Status:** Approved  
**Date:** 2026-11-06  
**Related Requirements:** NFR-008, NFR-012, NFR-015, PRC-001, PRC-002  
**Related Specifications:** SPEC-032, SPEC-036, SPEC-044, SPEC-045, SPEC-046

---

## Context

The portfolio requires a controlled development and deployment process.

The approved requirements include:

- Secure WordPress implementation
- Maintainable source code
- Backup and recovery
- Traceability
- Change control
- Staging and production validation

Development should not be performed directly on the production website.

---

## Options Considered

### Option A — Direct Local-to-Production Deployment

Develop locally and deploy directly to production.

**Advantages:**
- Simple
- Fewer environments
- Faster for very small changes

**Disadvantages:**
- Limited pre-production validation
- Higher production risk
- Reduced opportunity for accessibility, performance and regression testing
- Poorer separation between development and production

---

### Option B — Local → Staging → Production

Use local development, a staging environment and production.

**Advantages:**
- Clear separation of environments
- Allows pre-production testing
- Lower production risk
- Supports accessibility, performance and regression testing

**Disadvantages:**
- Requires a staging environment
- Requires deployment discipline
- Slightly more operational complexity

---

### Option C — Local → Git → Staging → Production

Use local development with Git-based source control, followed by staging validation and controlled production deployment.

**Advantages:**
- Version-controlled development
- Clear change history
- Supports review and rollback
- Provides a staging validation layer
- Strong alignment with SDD traceability and change control
- Separates development, testing and production

**Disadvantages:**
- Requires Git workflow discipline
- Requires deployment process configuration
- Slightly more setup than direct deployment

---

## Decision

Use **Option C — Local → Git → Staging → Production**.

The approved deployment flow is:

```text
Local Development
       ↓
      Git
       ↓
    Staging
       ↓
Testing / Review
       ↓
  Production
```

---

## Development Environment

Local development will be used for:

- Theme development
- WordPress configuration development
- Content-model development
- Local functional testing
- Unit/integration testing where applicable

Production must not be used as the primary development environment.

---

## Git

Git will be the source-control mechanism for project artifacts including:

- Theme source code
- Tests
- Documentation
- Specifications
- Architecture
- ADRs
- Implementation plans
- Configuration that is safe to version-control

Secrets and environment-specific credentials must not be committed.

---

## Staging Environment

Staging will be used to validate changes before production.

Validation may include:

- Functional testing
- Responsive testing
- Accessibility testing
- SEO testing
- Performance testing
- Security testing
- Regression testing
- Content verification

---

## Production

Production will contain only an approved version of the project.

Direct development changes on production are prohibited except for controlled operational activities that cannot reasonably be performed through the deployment process.

Production deployment must occur after the relevant implementation and testing activities have been completed.

---

## Backup and Recovery

Production must have a backup and recovery mechanism covering:

- WordPress database
- Uploaded media
- Required configuration

The backup strategy must support restoration testing.

Detailed backup frequency, retention and restoration procedures will be defined during Technical Design and Deployment Planning.

---

## Reason

The Local → Git → Staging → Production model provides an appropriate balance between simplicity and engineering discipline.

It supports the project's SDD workflow by creating clear boundaries between:

- Development
- Version control
- Testing
- Review
- Production

It also reduces the risk of untested changes reaching the live portfolio.

---

## Consequences

### Positive

- Controlled deployments
- Version history
- Easier rollback
- Pre-production validation
- Better traceability
- Reduced production risk
- Supports SDD change-control requirements

### Negative

- Requires staging infrastructure
- Requires deployment discipline
- Adds some operational overhead
- Requires a defined process for database/media synchronization

---

## Constraints

The project must not introduce a complex CI/CD platform unless a concrete requirement justifies it.

The deployment mechanism should remain proportional to the size and complexity of the portfolio.

Hosting provider, deployment tooling and exact CI/CD implementation are intentionally deferred to Technical Design.
